Единый файл задания. Объединяет шесть лабораторных работ курса в один модульный проект.

Версия: v3. Все развилки закрыты, документ переработан под единую сдачу, PyTorch

Изменения v2 → v3 (смена оборудования): Tesla V100 больше не доступна. Рабочее место —

## 1. Цель и рамки

### 1.1. Исследовательский вопрос

Работа отвечает на один вопрос:

> **Насколько выигрывает специализированная архитектура у универсального
> полносвязного персептрона на данных с явной структурой, и за счёт чего именно?**

Универсальная теорема аппроксимации говорит, что достаточно широкий MLP приблизит любую
разумную функцию. На практике он проигрывает: не потому, что не может, а потому, что не
знает про структуру данных и вынужден выучивать её с нуля из ограниченной выборки.
Свёртка знает про соседство пикселей и трансляционную эквивариантность, рекуррентность
знает про порядок, графовый слой знает про произвольные связи. Решётка пикселей и цепочка
токенов при этом сами являются частными случаями графа, поэтому работа естественно
заканчивается графовыми сетями как обобщением всего предыдущего.

### 1.2. Три сквозные нити

**Нить А — «универсальная модель против специализированной».**
В каждом модуле специализированная модель сравнивается с полносвязным baseline при
сопоставимом бюджете параметров. В методичках лабораторных 3 и 6 это сравнение уже
требуется явно; здесь оно распространяется на все модули и становится осью работы.

**Нить Б — семейство энкодер-декодер.**
Автоэнкодер (узкое горло, MSE), U-Net (то же самое плюс сквозные соединения,
кросс-энтропия) и генератор pix2pix (тот же U-Net плюс состязательная функция потерь) —
это одна архитектура с двумя переключателями. В коде это один класс `EncDec` с флагом
`skips`. Раньше нить была растянута через три отдельные сдачи; теперь целиком лежит
в модуле M4.

**Нить В — единый протокол эксперимента.**
Один цикл обучения, одни колбэки, одинаковый замер времени и памяти, общий реестр
запусков, общая сводная таблица. Ни один эксперимент не запускается в обход `run_experiment`.

### 1.3. Чем работа не является

Формулируется явно, чтобы не переоценивать результат:

- это не новая архитектура и не новый метод;
- содержательная часть заданий восходит к официальным примерам Keras (pix2pix, U-Net на
  Oxford-IIIT Pet, MPNN на BBBP); они портированы на PyTorch, и происхождение указывается
  в тексте со ссылками;
- масштабы экспериментов учебные, выводы справедливы в пределах использованных данных
  и бюджетов обучения.

Собственный вклад — единый протокол, контролируемые сравнения с разбросом по сидам,
сопоставимые бюджеты параметров, абляция сквозных соединений внутри одного семейства
моделей и перенос всего этого в один связный кодовый каркас.

## 2. Закрытые решения

| Код | Решение | Следствие |
|---|---|---|
| **D1** | Oxford-IIIT Pet, занят за тобой, используется по максимуму | один датасет закрывает классификацию, сегментацию, шумоподавление, генерацию и графовый эксперимент |
| **D2** | PyTorch | код методичек портируется с Keras; развилка `Backend` из v1 удалена как избыточная |
| **D3** | `21 mod 3 + 1 = 1` → **пожар** | свой датасет для сегментации: изображения огня и пожаров |
| **D4** | единая курсовая, на занятиях показывается часть по текущей лабораторной | модули режутся по темам; для показа делаются тонкие «витрины» (§3.3) |
| **D5** | разработка — WSL2 на AMD-ноутбуке (CPU), обучение — Colab (T4), защита — ноутбук | код обязан работать без GPU; устройство пишется в каждый запуск; витрины не требуют ни GPU, ни интернета |

### 2.0. Что означает D5

Раньше документ исходил из постоянного доступа к V100. Теперь ресурсы другие, и это
меняет не содержание, а инженерию:

- **CPU — не запасной вариант, а основной режим разработки.** Всё, что связано с
  конфигами, данными, метриками, витринами, отлаживается на ноутбуке за секунды.
- **Colab — не «где-то ещё», а такой же исполнитель `run_experiment`.** Он получает тот
  же репозиторий и те же конфиги и возвращает те же json.
- **Сессия Colab может оборваться в любой момент.** Отсюда обязательное возобновление
  с чекпоинта (§4.1) — на V100 это было удобством, теперь это требование.
- **Защита не зависит от сети и GPU.** Витрина читает json из репозитория и рисует.
  Это решение из v2 внезапно стало главной страховкой всей работы.

### 2.1. Что даёт Oxford-IIIT Pet

`torchvision.datasets.OxfordIIITPet` отдаёт из одной загрузки два типа разметки:
`target_types="category"` (37 пород) и `target_types="segmentation"` (тримап из трёх
классов). Это позволяет прогнать один набор изображений через четыре разные задачи:

| Задача | Модуль | Что берётся из датасета |
|---|---|---|
| Классификация 37 пород | M2 | изображения + метка породы |
| Шумоподавление | M4 | только изображения, цель равна входу |
| Сегментация | M4 | изображения + тримап |
| Генерация фото из маски | M4 | тримап + изображения, направление обратное |
| Полуразмеченная классификация на графе | M5 | эмбеддинги из M2 + метки породы |

Пять задач, один датасет, пять семейств моделей. Это и есть та связность, ради которой
всё затевалось: сравнения перестают быть сравнениями «яблок с апельсинами».

Fine-grained классификация 37 пород вдобавок делает сравнение «заморозка против
разморозки» гораздо содержательнее, чем бинарная задача из примера методички, где
замороженный MobileNetV2 и так даёт около 98 % и разница тонет в шуме.

### 2.2. Что даёт PyTorch

Помимо того, что это стандарт в исследованиях, переход снимает три конкретные проблемы v1:

- **Битые ссылки на данные исчезают.** Cora приходит из
  `torch_geometric.datasets.Planetoid`, BBBP — из `torch_geometric.datasets.MoleculeNet`,
  Pet — из `torchvision`. Из внешних источников остаётся только C-MAPSS и собственный
  датасет по пожарам.
- **Ручная возня с молекулами не нужна.** `MoleculeNet` отдаёт BBBP уже в виде графов,
  featurization из методички (`AtomFeaturizer`, `BondFeaturizer`, ragged-тензоры) можно
  либо воспроизвести ради понимания, либо заменить готовым. Рекомендую воспроизвести
  сокращённо: это ровно то место, где понимаешь, что такое граф молекулы.
- **Маскирование последовательностей становится честным.** `pack_padded_sequence`
  вместо keras-масок, и пункт З1.3 методички лабораторной 3 (сортировка по длине,
  оптимальное разбиение на мини-блоки) выражается естественно, а не в обход API.

### 2.3. Стоимость переноса с Keras

Оценка по модулям, чтобы не было сюрпризов:

| Модуль | Сложность переноса | Комментарий |
|---|---|---|
| M1 | тривиально | несколько десятков строк |
| M2 | легко | `torchvision.models.mobilenet_v2(weights=...)`, заморозка через `requires_grad_(False)` |
| M3 | легко, местами приятнее | `nn.LSTM` + `pack_padded_sequence` чище оригинала |
| M4, U-Net | умеренно | промежуточные слои энкодера достаются через `create_feature_extractor` из `torchvision.models.feature_extraction` |
| M4, pix2pix | умеренно | код TF-туториала ложится один в один; есть эталон junyanz/pytorch-CycleGAN-and-pix2pix для сверки |
| M5 | легко | PyG сокращает `GraphConvLayer` из методички до нескольких строк |

Сам факт переноса — плюс для портфолио: он показывает, что ты понимаешь, что делает код,
а не копируешь ячейки. Это стоит отдельного абзаца в README.

## 3. Структура проекта

### 3.1. Принцип

Курсовая сдаётся целиком, но на каждом занятии нужно показать часть, относящуюся
к текущей лабораторной. Отсюда разделение:

- **содержание** организовано по темам (модули M0–M6);
- **порядок работы** следует порядку курса;
- **показ** обеспечивается тонкими «витринами» — по одной на лабораторную.

Витрина ничего не считает заново: она подтягивает сохранённые результаты из реестра,
выводит нужные графики и таблицы и сопровождается картой соответствия пунктам методички.
Открывается за секунды, что важно, когда преподаватель стоит рядом.

Три слоя документации не смешиваются:

| Слой | Где | Для кого | Тон |
|---|---|---|---|
| Витрина | `defence/labN.ipynb` | преподаватель на занятии | сухо, по пунктам методички |
| Отчёт | `README.md`, `reports/` | портфолио | вопрос → метод → результат → ограничения |
| Конспект | `notes/MN_*.md` | ты | как угодно, переписывается свободно |

## 4. Ядро (M0)

### 4.1. Требования

1. Ни один эксперимент не запускается в обход `run_experiment`.
2. Результат запуска — json в `results/runs/`, а не число в выводе ячейки.
3. Смена датасета, модели или сида — правка конфига, а не кода.
4. Витрины только читают реестр и рисуют, никогда не обучают.
5. **Устройство-агностичность.** Ни строчки `.cuda()` в коде моделей и данных.
   Устройство выбирается один раз в `engine.py` (`cuda` → `cpu`, с заделом под `rocm`)
   и прокидывается вниз. Любой эксперимент обязан запускаться на CPU — пусть медленно.
6. **Возобновление.** Каждый прогон пишет чекпоинт (веса, оптимизатор, номер шага/эпохи,
   состояние ГСЧ, история) не реже раза в N шагов. Повторный запуск той же конфигурации
   с тем же сидом подхватывает чекпоинт и продолжает, а не начинает заново.
   Без этого длинные прогоны на Colab невозможны в принципе.
7. **Smoke-режим.** Флаг `smoke: true` в конфиге урезает всё до 2 батчей на эпоху и
   2 эпох. Назначение: за 10 секунд на ноутбуке проверить, что конфиг, данные, модель,
   метрики и запись результата не падают, — и только потом отправлять на Colab.
   Результаты smoke-прогонов пишутся в `results/_smoke/` и в сводную таблицу не попадают.
8. **Артефакты разделены по весу.** json результатов — в git; веса, чекпоинты и данные —
   нет (§13.3).

### 4.2. Запись результата

```json
{
  "exp_id": "E4.7b",
  "name": "encdec_pets_skips_true",
  "seed": 0,
  "config_hash": "a3f21c",
  "data": {"name": "pets_seg", "n_train": 3312, "n_val": 368, "n_test": 3669},
  "model": {"params_total": 6134531, "params_trainable": 2891779},
  "train": {"epochs_run": 17, "steps_run": 4896, "early_stopped": true,
            "wall_time_s": 812.4, "wall_time_per_epoch_s": 47.8,
            "peak_mem_mb": 5821, "resumed_from_step": 0},
  "metrics": {"val_miou": 0.7012, "test_miou": 0.6968,
              "test_miou_boundary": 0.5411, "test_miou_interior": 0.8123},
  "history": {"x_unit": "epoch", "x": [], "loss": [], "val_loss": [], "val_miou": []},
  "env": {"torch": "2.5.1", "device": "cuda", "device_name": "Tesla T4",
          "host": "colab", "precision": "fp16", "num_workers": 2}
}
```

Три изменения против v2, все из-за D5:

- **`peak_gpu_mem_mb` → `peak_mem_mb`** плюс обязательные `device`, `device_name`, `host`
  (`colab` / `wsl`). Без них колонка «время» в сводной таблице бессмысленна: 40 секунд
  на T4 и 40 секунд на CPU — разные утверждения.
- **`history` получает явную ось `x` и `x_unit`** (`epoch` или `step`). Для pix2pix
  история пишется по шагам, а не по эпохам, иначе задание З1.1 лабораторной 5 («извлечь
  данные из логов и найти оптимальную точку») не на чем выполнять: эпох там по сути нет.
- **`resumed_from_step`** — честно фиксирует, что прогон склеен из двух сессий Colab.

**Имя файла:** `{exp_id}__{config_hash}__seed{n}.json`. Правило не косметическое: один
запуск — один новый файл, существующие файлы никогда не переписываются другим прогоном.
Благодаря этому реестр append-only и Colab с ноутбуком могут пушить результаты в одну
ветку без конфликтов слияния (§13.2).

`results.py` группирует запуски по `exp_id`, считает среднее и стандартное отклонение
по сидам и выводит `results/summary.md`. При агрегации он **отказывается усреднять время
по запускам с разным `device`** и в этом случае выводит время отдельными строками.

### 4.3. Что осталось от абстракции

Развилка `Backend` из версии v1 удалена: фреймворк выбран, и поддерживать двойной
интерфейс — чистое переусложнение. Но два правила из неё сохраняются, потому что дёшевы
и полезны сами по себе:

- `History` — обычный `dict[str, list[float]]`, а не объект фреймворка;
  метрики считаются в `core/metrics.py` поверх numpy, визуализация получает numpy.
- Архитектура описывается конфигом (`ModelSpec`), сборка модели — отдельная функция.
  Благодаря этому добавление новой архитектуры позже сводится к одному файлу в `models/`
  плюс конфиг.

### 4.4. Детерминизм и точность

- Сид фиксируется для `random`, `numpy`, `torch`, `torch.cuda`;
  `torch.backends.cudnn.deterministic = True`, `benchmark = False` при финальных прогонах.
- Полного детерминизма на GPU не добиваемся, вместо этого три сида и разброс.
- **Смешанная точность выбирается автоматически, а не прописывается в конфиге.**
  Функция `precision_policy(device)` возвращает тройку «устройство, dtype, нужен ли
  скейлер»:

  | Условие | dtype | GradScaler | Где встречается |
  |---|---|---|---|
  | CUDA, `is_bf16_supported()` | bf16 | нет | Colab с A100 / L4 |
  | CUDA, bf16 нет (T4, sm\_75) | fp16 | **да** | бесплатный Colab, основной случай |
  | CPU | fp32 | нет | ноутбук; bf16 на CPU не даёт выигрыша и мешает воспроизводимости |

  Конфиг может только **запретить** AMP (`amp: false`), но не может потребовать dtype,
  которого на устройстве нет. Фактически выбранная точность пишется в `env.precision`
  каждого запуска. Замечание из v2 остаётся верным: на T4 (sm\_75), как и на V100,
  тензорные ядра есть под fp16, но bf16 и TF32 недоступны — так что связка
  «fp16 + обязательный скейлер» переносится с V100 на T4 без изменений.
- **Сравнивать числа между устройствами нельзя, и это касается не только времени.**
  fp16 против fp32 даёт расхождение в метриках в третьем знаке. Поэтому правило §5.7.

## 5. Протокол эксперимента

1. **Сиды.** По три на конфигурацию. Исключение — pix2pix (E4.10, E4.12), там один,
   и это оговаривается в тексте как ограничение.
2. **Разбиение данных.** Train / val / test фиксируются один раз на датасет и живут
   в конфиге. Отбор гиперпараметров — только по val, test трогается один раз в конце.
   Для Pet: официальный `trainval` делится на train и val, официальный `test` не трогаем
   до финала.
3. **Сопоставимость бюджетов.** Там, где сравниваются архитектуры разных семейств
   (нить А), приводятся варианты с примерно равным числом обучаемых параметров
   (в пределах ±20 %). Без этого сравнение ничего не значит.
4. **Ранняя остановка** везде, где не мешает задаче, с восстановлением лучших весов.
5. **Замеры.** Время обучения, пиковая память GPU, число параметров — записываются
   всегда, даже когда не требуются заданием.
6. **Отчётность.** Ни один вывод в тексте не опирается на число, которого нет в реестре.
7. **Однородность замеров.** Все запуски одной группы сравнения (например, E2.1–E2.4
   в нити А, или E4.7a против E4.7b) выполняются **на одном устройстве, с одной
   точностью, с одинаковыми `num_workers` и `batch_size`**. Если группа переезжает
   на другое устройство — переезжает целиком и перезапускается целиком. Полугруппа
   с ноутбука и полугруппа с Colab в одну таблицу не сводятся.
   Единственное сознательное исключение — E5.3, где сравнение CPU и GPU и есть задание.
8. **Отбор гиперпараметров — на ноутбуке, на уменьшенных данных.** Перебор конфигураций
   (E1.2, E5.2, E5.4) не занимает GPU-квоту: он идёт локально на подвыборке, а на Colab
   уезжают уже только финальные три сида. Квота Colab — расходуемый ресурс, и её тратят
   на финальные прогоны, а не на поиск.

**Данные для задания 1.** Встроенного Reuters в PyTorch нет, `torchtext` переведён

**Про маскирование — отдельный пункт, его спросят.** Задания З1.3 и З2.9 требуют
«проверить, что в модели включено маскирование нулей». В Keras это флаг `mask_zero`,
в PyTorch маски как таковой нет: `pack_padded_sequence` не маскирует нули, а просто
не подаёт их в рекуррентный слой. Формально это строже, но на защите ответ «у меня
вместо маски упаковка» звучит как отговорка. Поэтому в E3.4 добавляется **явная проверка
эквивалентности**: один и тот же батч прогоняется дважды — с упаковкой и с padding
без упаковки — и показывается, что выходы на реальных позициях совпадают, а при
отключённой упаковке нули меняют результат. Это две ячейки кода и один график,
зато пункт методички закрыт не словами, а измерением.

текстовых файла суммарно около 11 МБ, поэтому вместо охоты за живым зеркалом при каждом
запуске данные один раз кладутся в релиз собственного репозитория, а
`scripts/get_cmapss.py` тянет их оттуда. Внешняя зависимость исчезает совсем — важно,
когда одно и то же окружение поднимается заново в каждой сессии Colab. Предобработка по пунктам З2.2–З2.6: группировка
по идентификатору двигателя, ресурс как разность максимума и текущего такта, удаление
константных сенсоров, нормализация, обрезка целевой переменной на уровне 150 тактов.

**E3.6** замыкает регрессию из E1.1 на последовательности: та же метрика RMSE, но вход —
плоское окно без учёта порядка. Разница с E3.7 даёт вклад рекуррентности напрямую.

**Бюджет:** минуты на эксперимент, самое дорогое — прогоны нескольких схем батчинга.
**Устройство: весь M3 делается на ноутбуке.** Модели маленькие (BiLSTM на 128 единиц,

обучения**, и это сравнение обязано идти на одном стабильном железе. Colab с его
переменной загрузкой и делением GPU для замеров времени подходит хуже, чем локальный
CPU: там разброс между двумя запусками одного конфига может превысить измеряемый эффект.
Это не компромисс, а более правильный замер.
**Готовность:** BiLSTM устойчиво выше baseline по трём сидам в обеих задачах,
таблица «время обучения против схемы батчинга» заполнена, все замеры с одного устройства.

| E4.9 (пожар, ~100 изображений) | Colab T4, при нужде ноутбук | минуты: датасет крошечный |
| E4.11, E4.13 (pix2pix) | Colab T4 | см. ниже |

**pix2pix на T4 — единственное место, где план пришлось менять по существу.**
30 000 шагов при размере пакета 1 занимали 1.5–2.5 часа на V100; на T4 это 4–7 часов.
Бесплатный Colab столько не держит: отключение по простою наступает примерно через
90 минут без взаимодействия, а суточная GPU-квота исчерпывается быстрее. Решение
из двух частей:

1. **Целевой бюджет — 12 000–15 000 шагов вместо 30 000.** Для заданий лабораторной 5
   этого достаточно: З1.1–З1.3 требуют найти по логам точку оптимума и показать, что она
   не совпадает с последней итерацией. Расхождение валидационной L1 и визуального
   качества проявляется задолго до 30k. Урезание — не подгонка, а сознательное решение,
   и оно идёт в раздел ограничений (§M6) вместе с числом шагов.
2. **Возобновление обязательно** (§4.1, п. 6): чекпоинт каждые 500 шагов в Drive.
   Прогон, склеенный из двух сессий, помечается `resumed_from_step` и остаётся валидным.

Отсюда же следует, что **E4.14 (pix2pix на собственном датасете) режется первым** среди
опциональных: он стоит ещё одного такого прогона и не покрывает ни одного пункта методички.

**Готовность:** абляция E4.7 заполнена с разбросом; оптимальная точка pix2pix найдена
по логам (история по шагам, §4.2); собственный датасет собран, размечен, модель проверена
вне выборки.

### M5 — Графы (лаб. 6)

Конспект: **подробно**. Что разобрать: передача сообщений как обобщение свёртки; почему
решётка и цепочка — частные случаи графа; трансдуктивная постановка на Cora и чем она
мешает интерпретации; oversmoothing и зачем сквозные соединения внутри GNN; почему
readout обязан быть инвариантен к перестановке вершин и откуда здесь берётся трансформер.

| ID | Эксперимент | Покрывает |
|---|---|---|
| E5.1 | Референсная полносвязная модель на Cora | пример методички |
| E5.2 | GNN: тип агрегации, тип комбинации, число слоёв, dropout; доведение до устойчивого превосходства | З1.1, З1.2 |
| E5.3 | MPNN с трансформерным readout на BBBP, замер времени на GPU и CPU | З2.1 |
| E5.4 | Доработка MPNN до целевого качества | З2.2, З2.3 |
| E5.5 | **[О][М]** kNN-граф над эмбеддингами Pet из E2.6: GNN против MLP при малой доле разметки | нить А, замыкание |
| E5.6 | **[О][М]** То же на точках с плоскости из E1.3, дешёвая иллюстрация | — |

**E5.5 — финал работы.** Те же изображения Pet, что классифицировались в M2,
превращаются в граф ближайших соседей по эмбеддингам, и графовая сеть решает
полуразмеченную задачу: размечены, скажем, 5 % вершин. MLP видит только собственный
вектор объекта, GNN дополнительно видит соседей. Кривая «качество против доли разметки»
для двух моделей — это прямая проверка тезиса всей работы на данных, которые прошли
через всю работу. Эмбеддинги уже посчитаны в E2.6, обучение занимает секунды.

**По требованию З2.3 («выше 95 %»).** Тестовая выборка BBBP в методичке — 1 % данных,
это порядка 20 молекул; одна ошибка меняет метрику на 5 процентных пунктов. Такое число
статистически бессмысленно. Решение: основная метрика — ROC-AUC на валидации, она же
в сводной таблице; формальное требование методички выполняется и приводится отдельно
с оговоркой о размере выборки. Честная оговорка здесь выглядит лучше подогнанного числа.

**Бюджет:** Cora — минуты, **на ноутбуке**: граф целиком помещается в память, GPU
не нужен, и весь перебор из E5.2 идёт локально. MPNN на BBBP — 40–60 минут на T4.
E5.5–E5.6 — секунды на ноутбуке, эмбеддинги уже посчитаны в E2.6.

**Задание З2.1 (GPU против CPU) от смены железа только выиграло.** Раньше это был
искусственный лишний прогон на V100-хосте; теперь это ровно то, чем ты и так занимаешься
каждый день — один и тот же конфиг на ноутбуке и в Colab. Переключение среды выполнения
Colab на CPU даёт вторую точку замера в тех же условиях, а третьей строкой ложится
локальный AMD-CPU. Три устройства вместо двух, при этом ноль дополнительной работы:
`device` и так пишется в каждый запуск (§4.2). Для CPU-прогона число эпох урезается,
и это оговаривается — сравнивается время на эпоху, а не полное время обучения.
**Готовность:** GNN устойчиво выше baseline по трём сидам; AUC валидации зафиксирован;
сравнение GPU/CPU в таблице.

## 11. Окружение

### 11.1. Библиотеки

- **PyTorch 2.x** + `torchvision` (Pet, MobileNetV2, `feature_extraction`).
- **`torch_geometric`** — Cora через `Planetoid`, BBBP через `MoleculeNet`.
  В PyG 2.4+ базовые слои работают на чистых pip-колёсах: `torch-scatter` и
  `torch-sparse` компилировать не нужно. Это важно: сборка расширений на ноутбуке
  без CUDA — верный способ потерять вечер.
- **`rdkit`** — если featurization молекул воспроизводится вручную (пакет называется
  `rdkit`, старое имя `rdkit-pypi` заброшено).
- **`datasets`** (Hugging Face) или **`nltk`** — тексты для M3; `torchtext` не используем,
  он в режиме поддержки.
- **`torchmetrics`** — IoU, AUC, accuracy; единообразно и без самописных ошибок.
- **`hydra-core`** или простой yaml + `argparse` — решается при написании `config.py`.

### 11.2. Оборудование

| Роль | Что | Что на нём делается |
|---|---|---|
| Разработка и защита | AMD-ноутбук, WSL2, **CPU** | весь код, все конфиги, M1, M3, M5-Cora, E4.1–E4.2, все витрины |
| Обучение | Google Colab, **T4 16 GB, sm\_75** | M2, M4, MPNN на BBBP |

**Про GPU ноутбука — честно.** ROCm официально поддерживает узкий список дискретных
карт и на WSL2 работает только с частью из них; интегрированные Radeon (gfx1103 и
родственные) в списке отсутствуют, а обходные пути через `HSA_OVERRIDE_GFX_VERSION`
нестабильны и ломаются при обновлениях. `torch-directml` под Windows формально заводится
на любой DX12-карте, но отстаёт по версии torch и не покрывает нужные операции.
**Поэтому план строится на CPU-ноутбуке, а любой заработавший ROCm — приятный бонус,
не более.** Проверить, есть ли смысл пробовать, стоит один раз (§13.4) — и если нет,
забыть и не возвращаться.

Точность выбирается автоматически по §4.4; на T4, как и на V100, это fp16 с обязательным
`GradScaler`, так что этот кусок кода из v2 переносится дословно.

### 11.3. Версии

Правило v2 «версии фиксируются целиком, без диапазонов» **смягчается для torch**.
Причина: Colab поставляет собственную сборку torch, привязанную к своим драйверам CUDA.
Переустановка её на закреплённую версию стоит перезапуска среды выполнения, нескольких
минут в начале каждой сессии и регулярных конфликтов с предустановленными пакетами.

- `requirements-local.txt` — всё зафиксировано жёстко, torch из CPU-индекса
  (`--index-url https://download.pytorch.org/whl/cpu`).
- `requirements-colab.txt` — **torch и torchvision не указаны вообще**, берутся те, что
  уже стоят; фиксируется всё остальное. PyG ставится под фактическую версию torch.
- Фактические версии всё равно попадают в `env` каждого запуска (§4.2), так что
  воспроизводимость сохраняется в реестре, а не только в файле зависимостей.

## 13. Рабочий процесс: WSL ↔ Git ↔ Colab

### 13.1. Роли

Схема из трёх участников, у каждого одна обязанность:

```
  WSL2 (ноутбук)            GitHub                    Colab (T4)
  ──────────────            ──────                    ──────────
  пишем код          ──push──►  код                ──clone──►  тот же код
  smoke-прогоны                 конфиги                        запуск через
  лёгкие эксперименты           results/runs/*.json            scripts/run.py
  витрины, отчёт     ◄──pull──  (append-only)      ◄──push──   новые json
                                                                       │
                                                   Google Drive ◄──────┘
                                                   веса, чекпоинты, кеш данных
```

**Ключевое:** Colab пушит **только новые файлы результатов**, никогда не редактирует код.
Поскольку имя файла содержит `exp_id`, хеш конфига и сид (§4.2), два участника физически
не могут тронуть один файл — конфликтов слияния не бывает. Это единственная причина,
по которой такой двусторонний обмен вообще держится без боли.

### 13.2. Цикл

1. В WSL пишется/правится эксперимент, запускается со `smoke: true` — 10 секунд.
2. `git push`.
3. В Colab открывается `colab/run_on_colab.ipynb`: клон репозитория, монтирование Drive,
   `pip install -r requirements-colab.txt`, `python -m scripts.run exp=E4.7b seed=0,1,2`.
4. По окончании тетрадь копирует json в репозиторий и делает коммит с токеном,
   а веса — в Drive. Если сессия оборвалась, следующий запуск подхватит чекпоинт.
5. В WSL `git pull`, `make summary`, обновляется `results/summary.md` и витрина.

Обучённые веса **скачивать в WSL обычно незачем**: витрины рисуют по json, а не по весам.
Веса нужны только в двух местах — генерация картинок для отчёта (проще сделать там же,
в Colab, сохранив png в репозиторий) и E2.6 (эмбеддинги — файл на десятки мегабайт,
кладётся в Drive и оттуда же читается модулем M5, который и так работает на ноутбуке).
То есть ответ на вопрос «нужно ли гонять модели обратно»: **почти никогда**.

### 13.3. Что где живёт

| Артефакт | Размер | Где | В git? |
|---|---|---|---|
| Код, конфиги, витрины, конспекты | КБ | репозиторий | да |
| `results/runs/*.json` | КБ | репозиторий | **да, это главный артефакт** |

Правило одной строкой: **в git уезжает всё, что можно прочитать глазами.**

### 13.4. Настройка WSL — что важно сделать сразу

- **Репозиторий держать внутри файловой системы WSL** (`~/work/nn-inductive-biases`),
  а не в `/mnt/c/...`. Обращение к диску Windows через WSL медленнее в разы, и на
  `DataLoader` с несколькими воркерами это заметно сразу.
- `git config --global core.autocrlf false` — иначе Windows-переводы строк приедут
  в репозиторий и любой diff станет нечитаемым.
- Python через `venv`, не через системный; `python3-venv` доустанавливается отдельно.
- Один раз проверить, видит ли torch GPU: если `torch.cuda.is_available()` возвращает
  ложь на CPU-сборке — это ожидаемо и правильно, план на этом и построен.
  Возиться с ROCm имеет смысл только при дискретной карте из официального списка
  поддержки (§11.2); во всех остальных случаях время лучше потратить на разметку пожаров.
- Jupyter запускается в WSL, открывается в браузере Windows по `localhost` — витрины
  показываются с ноутбука без каких-либо дополнительных движений.

### 13.5. Запасной вариант, если Colab окажется тесен

Не паниковать и не менять архитектуру проекта. По порядку применения:
уменьшить разрешение M4 со 128 до 96; сократить число сидов с трёх до двух с явной
оговоркой; урезать pix2pix до 8k шагов; вырезать опциональные `[О]` эксперименты
в порядке §10. Ни один из этих шагов не трогает ядро и не рушит ни одного пункта
методички — именно ради этого бюджеты и вынесены в конфиги.
